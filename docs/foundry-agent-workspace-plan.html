01 / Objective

Own the coding workflow.

Deliver the useful core of a Codex-style desktop experience: persistent tasks, streaming conversations, coordinator and child agents, isolated worktrees, command approvals, captured output, and diff review. Model inference uses the user's configured Azure Foundry deployments; repository tools execute locally.

The first release includes parallel delegation. A coordinating agent assigns bounded work to specialists, collects commits and validation evidence, integrates changes into the task branch, and validates the combined result. Independent concurrent chats alone do not satisfy this objective.

Success means a real Windows repository task can go from request to coordinated implementation and tested, reviewable changes, with cancellation and restart recovery working throughout. Full editing and debugging remain in an external editor.

02 / Product decisions

Keep the agreed scope.

Included in v1

  • Electron desktop: task sidebar, conversations, agent tree, activity, approval queue, file browsing, and read-only Monaco diffs.
  • Direct Foundry model adapters: Responses, Chat Completions, and Anthropic Messages.
  • Coordinator plus specialists, bounded concurrency, isolated branches and worktrees, serial integration.
  • Persistent history, usage budgets, context management, MCP tools, Windows installer.

Deferred

  • Full editor, language servers, debugger, and built-in three-way merge UI.
  • Browser automation, scheduled tasks, hosted execution, team administration, and automatic updates.
  • Automatic provider fallback, autonomous publication, and automatic merges into the user's main branch.
  • Mandatory LiteLLM integration. A proxy can be evaluated later behind the same capability gate.

Default model is selected during onboarding. No Claude-first assumption or model-family inference from deployment names. Availability and API compatibility must be verified against the user's actual deployments.

03 / Architecture

One runtime owns execution.

Current state

Target design

Technology and ownership

Use a pnpm TypeScript monorepo: apps/desktop, packages/runtime, packages/protocol, and packages/providers. Use electron-vite, Zod, better-sqlite3, bundled ripgrep, Vitest, Playwright, and electron-builder. Pin supported versions at bootstrap and record them with deployment probe results.

The renderer never executes tools, reads SQLite, or calls models. Main protects credentials with Windows-backed Electron safeStorage and passes them to the runtime through private IPC. The runtime writes SQLite in WAL mode; the UI reconstructs its state from snapshots and ordered events.

IPC, credentials, and packaging decisions

Run the runtime using Electron's binary with ELECTRON_RUN_AS_NODE=1; verify this launch path and native SQLite ABI in an early packaged smoke build. Keep stdout exclusively for RPC, logs on stderr with redaction, validate both sides with Zod, and bound message sizes.

Enable renderer sandboxing and context isolation, disable Node integration, apply a local-only Content Security Policy, deny unsolicited permission requests, and gate external links. The credential form permits transient entry only: clear it after transfer to main and never retain credentials in renderer stores. Support Entra authentication where the deployment supports it and protected API keys otherwise; do not assume identical auth scopes across providers.

Ship a per-user Windows NSIS installer. Bundle ripgrep and rebuild/unpack native modules for the pinned Electron ABI. No automatic updater in v1. Validate installation on a clean Windows profile.

04 / Runtime contracts

Shared orchestration, faithful adapters.

Probe actual capabilities

Require streamed text, valid tool arguments, tool-result continuation, and cancellation before enabling coding. Probe parallel tool calls, reasoning continuity, cache support, and usage reporting separately; unavailable optional capabilities disable the associated feature. Missing usage remains “unknown,” never zero. Block configurations that cannot support enforceable token budgets until a conservative accounting limit is configured.

The agent loop

Assemble instructions and context → stream a model response → validate complete tool calls → authorize → execute → append tool results → continue until completion or a limit. Never execute a partially streamed tool call. Use provider-specific continuation rules, including signed or opaque blocks when required.

Context, errors, and budget behavior

Respect repository instructions under the application's policy hierarchy; repository and tool content cannot grant tool permissions. Retrieve relevant files using search before adding an indexing service. Keep user intent, acceptance criteria, approvals, and evidence references as durable records outside summaries.

Start with a bounded full transcript. Add explicit, previewable compaction before release: retain originals locally, record summarized ranges, preserve complete tool-call/result units and provider-required continuation, and fail visibly if the new context is invalid. Tool output is bounded with head/tail excerpts and an explicit truncation marker; secret-screened local output can retain supporting evidence.

Default to 50 tool iterations per user turn, a 64 KB tool-result excerpt, and three simultaneous model/tool execution slots across the app. Configure per-profile request limits and per-task token budgets; warn at 80%, stop at 100%. A coordinator waiting for children releases its slot. Child usage rolls into the parent's budget without double counting.

Honor rate-limit retry timing; use bounded exponential backoff with jitter for transient request failures. Coordinate SDK and runtime retries so attempts do not multiply. Do not retry completed side effects, switch models silently, or replay tool calls after interrupted streams. Surface useful provider errors after secret redaction. Monetary estimates require configured pricing and defined provider-specific cache accounting.

05 / Execution & recovery

Make every change attributable.

Worktree and coordination model

Create one integration worktree per task and one worktree per editing child from a recorded base commit. Use app-owned paths under %LOCALAPPDATA%/FoundryAgentWorkspace/wt and task branches under codex/. Preserve the user's main checkout and uncommitted changes. Use local refs by default; network fetch requires an explicit action.

The coordinator owns scope assignments and serial integration. Permit no nested child delegation in v1. Children return commits and evidence; the coordinator checks their scope, cherry-picks into its integration worktree, and reruns affected checks. Conflicts move the task to a visible blocked state with an external-editor resolution path. Completion requires combined-result validation, not merely successful child reports.

Tools and permission defaults

  • Read/search: worktree-scoped; enforce secret-path restrictions consistently across file reads, search, diffs, previews, and outgoing context.
  • Edit: exact-string replacement with an expected content hash and a unique match; create/overwrite has an explicit precondition. Reject stale edits and writes to Git metadata.
  • Commands: require approval of the exact command, canonical directory, shell, and environment changes. Non-interactive PowerShell by default, captured stdout/stderr, closed stdin, ten-minute default timeout.
  • Remembered approvals: opt-in per agent/worktree and task; visible and revocable. Invalidate on relevant executable/build-file changes, external modifications, or integrations. Recompute the fingerprint before execution.
  • MCP: configured servers only, explicit launch/network permission, per-tool approval or a user-managed allowlist. Server annotations never grant permissions.
  • Git: app-owned worktree setup is authorized by task creation. Present an explicit per-task grant for child commits and integration. Push, PR creation, discard, and main-branch integration remain separate user actions.
Approval is not sandboxing. Approved commands run with the user's Windows privileges and can access resources outside the worktree. Explain this in the approval UI. Strip app model credentials from child environments; path guards and redaction reduce exposure but do not make arbitrary commands safe.
Windows boundaries and process cleanup

Canonicalize through existing ancestors, follow symlinks/junctions, and verify containment using separator-aware comparisons. Test UNC/device paths, alternate data streams, drive-relative names, reserved devices, mixed casing, short names, trailing dots/spaces, and Git worktree pointer files. Revalidate at access time; explicitly assess path-swap races and remaining host-filesystem risk.

Apply deny rules for common credential files and redact detected secrets before any model request, UI output, persistence, or export. Secret detection is defense in depth, not a completeness guarantee. Protect local histories and diagnostic files with user-scoped access.

Cancel the model request and stop the command process tree. Capture process identities while alive; verify descendants actually exited before reporting cancellation or deleting worktrees. Start with tested Windows tree termination; if descendant tracking cannot prevent orphans or PID ambiguity, require a Job Object implementation before release. No PTY dependency in v1.

Persistence, restart, and agent handoff

Persist tasks, agents, assignments, dependency states, provider-native messages, tool intents, approvals, integration operations, usage, and an ordered event stream. SQLite is the only writer authority; use transactional state changes and numbered migrations with pre-migration backup.

Write execution intent before mutations, including edits, commands, commits, and integration. A runtime crash changes unfinished operations to unknown outcome. Reconcile file hashes, Git state, and surviving processes before any retry; ask the user when outcome remains uncertain. Never interpret an interrupted operation as successful.

Cancellation produces a provider-valid continuation without inventing a successful tool result. Restart reconnects the UI to stored state and revokes pending approvals. Cancel one child without affecting siblings; cancel the parent stops its descendants. Preserve partial work and evidence until the user explicitly discards them.

07 / Release evidence

What “done” must prove.

  • Each supported API adapter completes a coding task on a verified deployment; at least two upstream model families pass. Probe reports identify exact endpoint/profile fingerprints and unsupported capabilities.
  • Two child agents produce separate commits, and the coordinator integrates and validates them without altering the user's main checkout.
  • Unapproved commands, forged/stale approval responses, path escapes, Git metadata edits, and secret-file exposure are rejected in relevant tool paths.
  • Build/executable changes invalidate remembered approvals. Scope violations and integration conflicts are visible and do not silently overwrite work.
  • Stream cancellation and nested command termination work; restart reconciles unknown effects without duplicate execution.
  • Rate limits, budget exhaustion, dependency failure, missing usage, and unavailable providers produce truthful, recoverable states.
  • Compaction preserves required context and provider continuation; MCP tools obey the same execution policy.
  • Credential canaries remain absent from outgoing unauthorized content, renderer stores, logs, SQLite, and diagnostics. Known detection limits are documented.
  • Automated suites, independent review, and a clean Windows installation pass for the release build; final integrated tests and reviewer findings are retained.

These are acceptance criteria, not current test results. Azure probes incur usage and run only when implementation testing is authorized.

These capabilities belong to the baseline at f75d1ed, documented in implementation-status.md. They are not dependent on the unfinished orchestration branch.

Typed private JSON-RPC connects a supervised runtime to Electron main. SQLite WAL is written only by the runtime; credentials use the OS-backed vault.

  • Provider execution: Responses, Chat Completions and Anthropic native tool-call/continuation adapters, injected-transport fixtures and capability qualification. Complete validated tool calls execute after provider completion. Opaque reasoning/signatures stay outside renderer history; failed fresh probes invalidate prior qualification.

  • Reviewed mutations: one-shot edit/command decisions bind task, nonce and exact proposal. Edit review includes before/after content; command review includes script, directory, shell, environment, timeout and repository fingerprint. Replayed or stale approvals fail closed.

  • Windows execution: suspended process creation, Job assignment before execution, bounded output, minimal environment, timeout/cancellation, runtime-parent death handling and descendant cleanup evidence. These commands still run with the user's Windows privileges.
  • Resource limits and local packaging: three shared model/command execution slots, no slot held for approval waits, conservative token reservations and bounded turns. A per-user 0.2.0 installer candidate and packaged smoke path exist; they are not a signed or clean-profile-qualified v1 release.

6. Known limitations and retained safeguards

  • File-tool creation of new files remains disabled pending a safe Windows directory-relative primitive. Existing-file edits remain the supported path.
  • Command fingerprinting rejects worktrees beyond 10,000 files or 64 MiB, including dependency folders. Commands start with a Windows-only PATH; developer tools need explicit paths or a reviewed PATH setting. Scalability/tool discovery remain usability work.
  • Commands run with the user's account privileges. Worktree isolation and approval are not OS sandboxing, and arbitrary scripts can reach outside their declared repository scope.
  • Approvals remain one-shot. Remembered approvals, autonomous publication, automatic conflict resolution, destructive worktree cleanup and silent provider fallback are not introduced by this milestone.
  • User database upgrades require separate in-app confirmation and a verified backup. The old binary cannot open schema v2; rollback must restore a separate verified v1 backup without overwriting later history.
  • No existing-user-data migration, actual paid Foundry probe, source/main integration, remote push or deployment is represented as complete by the local fixture results.

00 / System Architecture

The Non-Negotiable Invariants

Before writing a line of code or installing a dependency, you must internalize the five structural boundaries that make this system durable. An agent rebuilding this codebase may swap specific libraries or tools, but violating these boundaries breaks the core safety and recovery model:

1. The Single-Writer Rule

Only the background Node.js runtime process may ever connect to or write to SQLite. The Electron main process supervises the runtime child over private stdio JSON-RPC 2.0. The React renderer is completely sandboxed: it holds no SQLite handles, no direct Node APIs, and reconstructs state strictly from immutable snapshots and push events.

2. Process Tree Reclamation

Windows commands and MCP servers do not run as untracked child processes. Every execution must be spawned in a suspended state (or immediately bound) into an operating system Windows Job Object configured with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. When a command times out, cancels, or the host exits, zero orphan processes survive.

3. Pre-Mutation Intent Persistence

Never perform a disk, Git, or tool side effect before recording the intent in SQLite. If the runtime terminates mid-mutation, the operation restarts into an explicit unknown outcome. Interrupted mutations must never be blindly re-executed or assumed successful; they require read-only reconciliation.

4. Approval Defense-in-Depth

Tool execution requires explicit user authorization. Each proposal binds a unique cryptographic nonce, task ID, working directory, script, environment, and repository fingerprint. File edits require an exact SHA-256 hash precondition. Path traversal guards reject UNC device paths (\\.\), NTFS Alternate Data Streams (:stream), short-names (8.3), and directory junctions.

Zero-Paid-Network Testing Invariant: Routine automated test suites (unit, integration, and E2E) must execute 100% offline using deterministic mock/fixture providers. Real Azure Foundry credentials and network calls are isolated exclusively to optional pre-deployment qualification CLI runs.

Phase 02

Storage & Recovery Engine (packages/runtime)

Implement the single-writer SQLite store, pre-mutation intent logging, and credential canary redaction engine.

Milestone 2: SQLite Store & Secret Redaction 5 Steps
Configure database with PRAGMA journal_mode = WAL;, PRAGMA synchronous = NORMAL;, and PRAGMA busy_timeout = 5000;. Enforce single-writer by opening connections only in the runtime.
Version database schema with PRAGMA user_version. Before executing an upgrade migration, create a verified .bak file copy. If migration fails, restore the backup.
Before executing edits, commands, commits, or retirement, insert a record into execution_intents. If a crash occurs, restart reconciles the state and marks unresolved operations as unknown.
Build a Redactor class. For every registered secret, register its literal needle PLUS its JSON string-escaped variants (escaping \, ", and \n). Add regex heuristics for raw bearer tokens and private keys.
Test runtime simulated crash: assert unstarted usage reservations reset cleanly to 0 tokens without leaking budget, and pending approvals transition to revoked/unknown.
Exit Gate 2: Database integrity check passes (PRAGMA integrity_check) and tests verify zero secret canaries escape into SQLite WAL, logs, or diagnostic dumps.
Phase 03

Process Isolation & Tool Policy

Implement Windows Job Objects, path traversal defense, and one-shot reviewed mutation execution.

Milestone 3: Job Runner & Policy Service 5 Steps
Use Windows Win32 API via P/Invoke or native C++ addon to create an anonymous Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. Create process suspended, assign to job, then resume thread.
# Essential Win32 Job Object configuration pattern
$job = [JobManagement]::CreateJobObject([IntPtr]::Zero, $null)
$info = New-Object JOBOBJECT_EXTENDED_LIMIT_INFORMATION
$info.BasicLimitInformation.LimitFlags = 0x2000 # KILL_ON_JOB_CLOSE
[JobManagement]::SetInformationJobObject($job, 9, [ref]$info, ...)
[JobManagement]::AssignProcessToJobObject($job, $processHandle)
Canonicalize paths through existing ancestors. Reject paths containing UNC device prefixes (\\.\, \\?\), NTFS Alternate Data Streams (:stream), 8.3 aliases, and directory junctions pointing outside the worktree.
Editing tools must require an expectedHash parameter matching the SHA-256 of the target file before modification. Exact string match must occur exactly once. Reject stale edits and writes to .git/ metadata.
Commands require user approval binding the cryptographic nonce, exact script, working directory, environment overrides, and worktree fingerprint. Fingerprint re-checks before execution.
Create tests/integration/security-audit.test.ts testing path traversal bypasses, canary leaks in MCP stderr, and orphan process termination on command timeouts.
Exit Gate 3: Background child processes (e.g. cmd.exe /c start ping 127.0.0.1 -t) terminate completely upon parent command timeout or cancellation.

Phase 05

Worktree Lifecycle & Multi-Agent Coordination

Implement isolated task worktrees, coordinator delegation, and serial cherry-pick integration.

Milestone 5: Git Worktrees & Coordinated Orchestration 5 Steps
Create isolated worktrees under %LOCALAPPDATA%\FoundryAgentWorkspace\wt\<taskId> on dedicated branches (codex/task/<taskId>). Ensure the user's main checkout and working files are never dirtied.
Coordinator plans assignments with bounded scopes. Concurrency is limited (e.g. max 3 active execution slots across the application). Coordinator waiting on children releases its execution slot.
Children stage only files matching their approved scope. Verify .gitattributes, reject gitlinks and embedded repos, and commit with recorded parent commit hashes.
Coordinator cherry-picks child commits serially into the integration worktree. If conflicts occur, preserve CHERRY_PICK_HEAD, transition task to a visible blocked state, and provide an external editor resolution path.
Execute required validation command on the final combined tree. Allow worktree retirement only when Git proves the tree is 100% clean (no untracked or uncommitted files).
Exit Gate 5: tests/integration/orchestration.test.ts passes: two child agents execute independent worktrees, coordinator integrates serially, and combined tests pass with the main checkout untouched.

Phase 07

Sandboxed Desktop Shell (apps/desktop)

Implement the Electron main process, secure IPC bridges, OS credential vault, and the React desktop interface.

Milestone 7: Electron Main, Security Gates & React UI 5 Steps
Spawn the background runtime using ELECTRON_RUN_AS_NODE=1 on private stdio. Supervise process lifecycle, restart on unexpected exit, and pipe events to BrowserWindow.
Use Electron safeStorage (Windows DPAPI) to encrypt API keys before persisting to disk. Pass credentials to runtime over private IPC only when a task or probe explicitly executes.
In ipcMain.handle, verify event.senderFrame === window.webContents.mainFrame. Because URL.origin is "null" for file: schemes, compare schemes and pathnames explicitly and fail closed.
// Essential IPC sender and origin authorization pattern
const authorize = (event) => {
  if (!window || event.sender !== window.webContents || event.senderFrame !== window.webContents.mainFrame)
    throw new Error('Untrusted IPC sender.');
  let actual;
  try { actual = new URL(event.senderFrame.url); } catch { throw new Error('Untrusted IPC origin.'); }
  if (actual.protocol !== expectedUrl.protocol || actual.pathname !== expectedUrl.pathname)
    throw new Error('Untrusted IPC origin.');
};
